## 3. Methodology

### 3.0 Research approach and design

This project adopts a **quantitative, comparative experimental methodology**: two group-approach policies — a hand-engineered geometric rule and a Behavioural-Cloning model trained on non-expert demonstrations — are evaluated against each other and against naive baselines, using the same world, the same start conditions, and the same evaluation metrics, so that policy choice is the only varying factor (Objective 4). This is deliberately a controlled-comparison design rather than an exploratory or qualitative one, for two concrete reasons worth stating critically rather than assuming as obvious. First, the research question itself — *"does a learned policy outperform a rule-based one on measurable approach-pose accuracy?"* — is a comparison-of-means question, which quantitative methods are suited to answer with a defensible pass/fail threshold (Objective 4's <0.4 m / <20° criteria), whereas a qualitative approach (for example, interviewing bystanders about how an approach *felt*) would require running the actual robot around real human participants, which is outside this project's ethical and time scope (Section 3.7). Second, the PLUS-HRI dataset itself is a fixed, already-collected corpus of non-expert teleoperation demonstrations rather than something this project could redesign as a live study, which fixes the appropriate methodology to *retrospective analysis and offline learning* from existing behavioural traces, followed by a live simulation comparison, rather than new data collection.

The corresponding methodological limitation, stated plainly rather than left implicit: every metric used in this project (approach-position/orientation error, O-space intrusion, minimum distance to person, task success) is a *geometric proxy* for social acceptability, not a direct measurement of how a human bystander would actually feel about the approach. This is a standard and accepted simplification in the social-robot-navigation literature reviewed in Chapter 2 (Kruse *et al.*, 2013; Ríos-Martínez, Spalanzani and Laugier, 2015), but it is a real gap between what is measured and what ultimately matters, and is treated in this project as an accepted, explicitly-stated limitation rather than something resolved — resolving it fully would require real human-participant testing, which this project's ethical scope (Section 3.7) does not cover.

The overall system pipeline that the rest of this chapter describes, in order, is:

```
recorded PLUS-HRI demonstrations  →  extraction & labelling  →  offline BC/rule training & evaluation
                                                                          ↓
Gazebo simulation (TIAGo + hand-built world)  →  live perception  →  group/O-space estimate  →  policy (rule | BC)  →  Nav2  →  metrics
```

Both the offline (Section 3.2–3.4) and live-simulation (Section 3.5–3.6) halves of this pipeline are described below, since the dissertation's Objective 4 comparison is only fully meaningful once both are in place.

### 3.1 Dataset

The PLUS-HRI dataset consists of 24 recorded non-expert teleoperation sessions. Direct inspection (rather than assuming the format was uniform across all 24) established that the dataset in fact spans **two distinct recording generations**: sessions 1 and 3 alone carry full per-frame facial-landmark and gaze annotations (`facial_landmarks_uniface.csv`, `gaze_uniface.csv`), recorded under an earlier pipeline, while the remaining 22 sessions were recorded later, in a segmented-clip format carrying only `cmd_vel.csv`, the operator's own raw eye-gaze coordinates (not a human subject's), the robot's own head pan/tilt joint state, and joystick input — with no person-position ground truth of any kind. This asymmetry is the single fact that shapes the whole extraction methodology below: sessions 1 and 3 function as the project's only source of ground truth for validating a person detector (Section 3.2) and, later, its own O-space estimate (Section 3.3), while all 24 sessions contribute to the Behavioural Cloning training data once a detector's own output — rather than the recording itself — supplies the missing human-position signal for the other 22.

Extraction was implemented in `extract_training_table.py`, reading each session's ROS1 bag files via the `rosbags` library's ROS1 reader and typestore, and merging pose (`/robot_pose`, `/mobile_base_controller/odom`, `/dlo_node/odom`), LiDAR (`/scan`), and person-detection topics onto a common timestamp index using `pandas.merge_asof`. Two dataset-specific defects were identified and corrected during this process, and are worth reporting methodologically rather than only as debugging notes, since both would silently corrupt results if left unstated: first, `cv2.CAP_PROP_POS_FRAMES`-based frame seeking on these session videos was found to decode corrupt, solid-green frames, so `extract_person_detections.py` reads frames strictly sequentially instead; second, an initial 0.1 s merge tolerance between `cmd_vel` and detection timestamps was found to drop 80–88% of rows to missing data, because the 22 segmented sessions' detections are sampled at roughly 1 Hz rather than per-frame — the tolerance was widened to 0.6 s (covering half the sampling gap either side, without changing which detection `merge_asof` selects as nearest) to recover genuine coverage. A separate, unrelated pitfall — `np.isclose`'s default relative tolerance (`rtol=1e-5`) evaluating to roughly 17,000 seconds on a ~1.76×10⁹ Unix timestamp, causing every detection in a session to spuriously match every frame — was corrected by passing `rtol=0` explicitly wherever timestamps are compared for equality.

Session-level train/validation/test splitting (`split_dataset.py`) allocates whole sessions to each split (70% train / 15% validation / remainder test) using a fixed random seed (42), so that no single session's rows appear in more than one split — a deliberate choice to prevent information leakage, since adjacent rows within one session are highly autocorrelated (near-identical robot pose and LiDAR readings a few tenths of a second apart) and would otherwise let a model "memorise" a session rather than generalise across them. Sessions 1 and 3 are deliberately forced into the training split rather than randomly assigned, because they are the only two sessions carrying real human-position ground truth and are too valuable, and too few, to risk holding one entirely out of training — a limitation stated explicitly here rather than discovered by a marker: **the person-perception validation in Section 3.2 and the O-space validation in Section 3.3 both therefore validate against sessions the Behavioural Cloning model was also trained on**, which is methodologically acceptable for validating the *perception and clustering pipeline* (a fixed, non-learned geometric procedure) but would not be acceptable for validating the *learned model itself* — which is why the Behavioural Cloning evaluation in Section 3.4 uses entirely separate, fully held-out test sessions (5, 9, and 59) that were never used for any training or tuning decision.

### 3.2 Person perception

Person detection uses **YOLOv8n**, a real-time single-stage object detector descending from Redmon *et al.*'s (2016) original "You Only Look Once" formulation (the specific YOLOv8 architecture is documented independently by Yaseen (2024), since Ultralytics did not publish a formal peer-reviewed paper alongside the release). This is a **documented substitution** for the proposal's originally named perception model, NVIDIA's LocateAnything-3B (Wang *et al.*, 2026) — the proposal's own risk table names "keep a simpler person-detection baseline" as an approved mitigation, so the substitution is a planned contingency rather than an undisclosed deviation.

The substitution was validated, not merely asserted. `validate_detector_recall.py` measures recall directly against the facial-landmark ground truth in sessions 1 and 3 — defined precisely as: of every moment where the ground truth confirms at least one face was genuinely present, what fraction did YOLOv8n also report at least one detected person in — and found **99.7% recall against the proposal's own 80% target**, comfortably satisfying Objective 2 on its own terms. To additionally test the substitution against the *named* model rather than only an arbitrary threshold, a direct head-to-head comparison (`run_locateanything_comparison.py`) was run on 30 ground-truth-positive frames from sessions 1 and 3: LocateAnything-3B reached 100.0% recall (30/30) at a measured 25.6 s/frame, versus YOLOv8n's 96.7% (29/30) at approximately 0.005 s/frame (~200 FPS). The recall gap is a single frame and the two detectors' Wilson 95% confidence intervals overlap heavily (88.6–100% vs. 83.3–99.4% at n=30) — **not a statistically meaningful difference at this sample size** — while the roughly 5,000× speed difference is unambiguous. This is reported as the project's actual justification: not that LocateAnything-3B was difficult to install, but that a direct, measured comparison found no meaningful accuracy advantage to offset a five-order-of-magnitude speed cost for a task requiring continuous, real-time detection. In the live simulation pipeline (Section 3.5), the detector remains selectable — YOLOv8n is the default for continuous perception, and LocateAnything-3B is available for one-shot demonstration of the proposal's originally named model, automatically switching the perception loop from continuous detection to a look-once-then-rely-on-Nav2's-own-obstacle-avoidance mode, since continuous detection at 25 s/frame is not operationally viable.

### 3.3 Group detection and O-space estimation

Group detection (`cluster_groups.py`) treats individually-detected people, per frame, as nodes in a similarity graph, linking two people into the same group when their pixel distance falls below a threshold expressed in units of their own average bounding-box width, rather than raw pixels — connected components of this graph become candidate groups. This normalisation is a deliberate, stated approximation for the absence of camera calibration or depth in the recorded video: bounding-box width shrinks with distance from the camera in roughly the same way true separation does, so measuring distance in "person-widths" partially cancels perspective distortion that raw pixel distance would not. This is reported as a documented simplification rather than true 3D localisation, and is one of the clearest places in the methodology where the recorded dataset's own limitations (no depth, no calibration) directly shaped the technical approach.

O-space estimation follows Kendon's (1990) F-formation framework — the shared, jointly-oriented space at a conversational group's centre — but could not use the framework's usual orientation-based construction, because direct inspection confirmed `gaze_uniface.csv` is **entirely empty** (100% null across all recorded columns, all sessions) — there is no per-person facing-direction ground truth anywhere in this dataset. The adopted fallback is the **mutual-facing assumption**: each group's O-space centre is approximated directly as the group centroid already produced by clustering. This is not an ad-hoc workaround; it is consistent with, and independently justified by, Vascon *et al.*'s (2016) game-theoretic F-formation detection method, which demonstrates that group structure can be recovered from relative *position* alone, without requiring orientation estimates at all — a result this project leans on directly to defend the mutual-facing fallback as a legitimate simplification given the data available, rather than a compromise made purely out of necessity. A candidate approach point is then computed (`estimate_approach_points.py`) by drawing a line from an assumed robot viewpoint through the group centroid and placing the standoff point just outside the group's extent along that line, facing back toward the centre — the same rule later re-applied, in real-world metric coordinates rather than image pixels, as the live rule-based baseline (Section 3.5.2).

Validating this pipeline required a hand-labelled ground truth that does not exist natively in the dataset, so one was constructed: `prepare_ospace_validation.py` exported 30 frames spanning 18 sessions (each containing a genuine 2+-person group), each annotated with the pipeline's own estimated O-space centre, for manual labelling of the true centre. The proposal's original criterion — an estimate within 0.3 m of the manual label for at least 70% of frames — could not be evaluated honestly, since 0.3 m is a metric tolerance and the underlying video carries no depth or calibration from which real metres could be recovered; reporting a metre figure here would be fabricated. The criterion was therefore re-specified, before use, as: **within 0.5× the mean detected person bounding-box width of the manual label, for at least 70% of labelled frames** — chosen because an adult's shoulder width is itself roughly 0.45–0.50 m, so 0.5× bounding-box width corresponds to approximately 0.22–0.25 m of real-world tolerance, preserving the original criterion's order of magnitude while expressing it in a unit this dataset can actually measure, and one that self-corrects for perspective (a person further from the camera receives a proportionally tighter pixel tolerance, which is the physically correct behaviour). This is disclosed here as a stated, deliberate methodological adaptation to a genuine data constraint, agreed with the project's supervisor rather than a marker discovering it independently — *[Saaru: confirm this sign-off actually happened before submission; the gap analysis flagged this as still outstanding as of your last update]*.

### 3.4 Behavioural Cloning model

**Label construction.** No stage of the raw teleoperation recording labels any moment as "this was a demonstrated group approach" — this had to be inferred. `build_approach_pose_dataset.py` identifies genuine approach events by finding transitions from sustained movement to a genuine stop, with a detected group present nearby at the stop; that stop's pose is then treated as the human operator's implicit judgement of "a good place to be near this group," and every row in the lead-up to that stop is labelled with the eventual stop pose as its prediction target. Raw `cmd_vel` in this dataset is extremely spiky — isolated single-sample non-zero values rather than sustained speed changes — so a naive sample-by-sample moving/stopped test found almost no usable segments; speed was instead averaged into 0.5-second bins before the moving/stopped test was applied, which recovered genuine, usable movement segments. This inference process identified **462 independent demonstrated approach events across all 24 sessions, expanding to 70,555 labelled rows** in `approach_pose_dataset.csv`.

**Target and feature design.** The prediction target is the demonstrated stop pose expressed **relative to the robot's own position and heading at prediction time** (Δx, Δy in the robot's forward/left frame, plus Δyaw), rather than an absolute map coordinate — a direct methodological consequence of an earlier, explicitly documented finding: absolute robot (x, y) as a *feature* in the first baseline model measured *worse* than omitting it, because raw position does not generalise across sessions recorded in different rooms; the same reasoning was judged to apply, if anything more strongly, to using absolute position as a *target*. The final feature vector (seven features, in a fixed order the deployed policy node must reproduce exactly) is: `lidar_min_range`, `lidar_mean_range`, `linear_x_prev`, `angular_z_prev`, `num_people`, `group_bearing_rad`, and `group_scale_norm`. Two of these — `group_bearing_rad` and `group_scale_norm` — replaced an earlier, weaker feature encoding (raw normalised pixel position, `group_center_x_norm`/`y_norm`) after that encoding was found to make essentially no difference to model accuracy; `group_bearing_rad` is a physically meaningful quantity (the group's angle off the robot's forward direction, computed from pixel x-position under a documented, uncalibrated assumption of a 58° horizontal camera field of view — a typical value for TIAGo's RGB camera, not measured directly), whereas a raw normalised pixel coordinate carries no directly interpretable geometric meaning and is tied arbitrarily to image resolution.

**Model architectures.** Two model families were trained and compared, per the proposal's committed architecture decision: a multi-layer perceptron (two hidden layers, originally specified as 128/64 units with ReLU activations) as the primary architecture, and a Random Forest regressor as a lower-variance, documented alternative — a sensible hedge given how few independent demonstration events (462) were available relative to the 70,555 expanded rows, since tree ensembles are typically more robust than neural networks to a small number of truly independent examples. Both were tuned via grid search (`grid_search_approach_pose.py`) exactly as the proposal's Research Methods section committed to: every candidate configuration was scored **only on the validation split**, with the test split held out entirely until a single winning configuration per model family was selected and finally evaluated once — avoiding information leakage from tuning decisions into the reported test result. Selection ranked candidates by mean validation position error (Euclidean distance in the (Δx, Δy) plane), since that is the quantity Objective 4 sets a numeric threshold on; orientation error was recorded alongside but not used for ranking, since a model that predicts orientation well while stopping in the wrong place is not useful for this task.

Tuning materially changed both models' results — Random Forest improved from 0.401 m/29.3° to 0.365 m/25.8°, and MLP from 0.465 m/42.2° to 0.395 m/31.0° — and, notably, the winning MLP configuration (32/16 hidden units, L2 regularisation α=0.1) is substantially smaller and more heavily regularised than the proposal's originally specified 128/64 architecture, which is itself a reportable methodological finding: **the proposed architecture was too large for the amount of independent demonstration data actually available**, not merely under-tuned.

**Evaluation.** `evaluate_approach_pose.py` compares four policies — a naive mean-prediction floor, the rule-based baseline (applied offline, approximating distance-to-group via `lidar_min_range` since no metric group distance exists in recorded data), the tuned Random Forest, and the tuned MLP — on the fully held-out test sessions (5, 9, 59; 11,921 rows), reporting both mean *and* median error (median is reported because a small number of large errors can dominate a mean and misrepresent typical performance) and the percentage of rows meeting each of Objective 4's thresholds independently, alongside the percentage meeting both simultaneously. This is a deliberately conservative reporting standard: a policy is not credited with "meeting the threshold" on the strength of its mean alone if that mean is pulled down by a minority of very accurate predictions.

### 3.5 Simulation environment and system integration

**Platform.** The live system runs on the TIAGo mobile-manipulator platform (Pagès, Marchionni and Ferro, 2016) in Gazebo, using ROS 2's Nav2 navigation stack (Macenski *et al.*, 2020) for path planning and execution — both cited here by their own system papers rather than only vendor documentation, since both are the actual software components this project's contribution sits on top of rather than merely background context.

**World construction.** The evaluation world (initially `restaurant_humans.world`, superseded during 17–20 August 2026 development by newer multi-group and seven-human test worlds) is hand-built rather than procedurally generated for the actor placements, using LIRS-HMLG humanoid actor models arranged into conversational groups; a separate parametric generator (`generate_social_world.py`) exists for quickly producing geometric variants (a 3-group/9-person "unseen" configuration for out-of-distribution testing, and an "adjacent" configuration for stress-testing whether clustering correctly separates two nearby groups) but the hand-built worlds remain the primary evaluation scenes, each shipping a `.groundtruth.json` file giving every person's exact position in real metres — this ground truth is what makes six of the eight evaluation metrics (Section 3.6) computable at all, since the recorded PLUS-HRI video never had metric position data to evaluate against. The occupancy map used by Nav2 is generated directly from each world's wall geometry (`world_to_map.py`), rasterising static collisions at laser height rather than running SLAM — a deliberate choice that produces an exact, drift-free map with no dependency on a successful mapping run, at the cost of requiring the map to be regenerated whenever the world geometry changes.

**Live perception.** `group_perception_node` closes the pixel-to-metres gap that constrained every offline stage: it subscribes to TIAGo's RGB and depth image streams and camera intrinsics, runs the chosen detector (Section 3.2), back-projects each detected person to real 3D coordinates using the depth image, transforms those coordinates into the map frame via TF, and clusters them into groups in genuine world coordinates — publishing a real-metres `/group_centroid` that both policy nodes consume identically. This is the point in the pipeline where, in the project's own framing, "offline data analysis becomes a robot system."

**Localisation.** Rather than relying on AMCL (which was found, in this container, never to converge reliably), localisation is provided by a dedicated ground-truth node (`gt_localisation_node`) that recomputes and publishes the map→odom transform continuously at 30 Hz from Gazebo's own simulator state, correcting for wheel-odometry drift in real time (T_map_odom = T_map_base × inverse(T_odom_base)). An earlier, simpler approach — publishing a single *static* map→odom transform once at startup — was found to be correct only for an instant and to diverge steadily afterward, particularly whenever wheel slip occurred (which collisions reliably cause), producing a cascade of downstream symptoms: the robot's Gazebo and RViz positions visibly diverging over a run, the costmap becoming offset from the real world, and — critically — detected people being placed at the wrong map coordinates because a correct camera-relative detection was transformed through a stale transform. This is reported here as a deliberate methodological choice with an explicit justification for the dissertation: **localisation was provided from simulator ground truth rather than AMCL, specifically so that navigation/localisation error could not confound the comparison between the rule-based and Behavioural Cloning policies** — the two policies are compared under identical, artefact-free localisation, isolating policy quality as the variable under test. All other navigation components (laser scanning, costmaps, global and local planning) operated normally through Nav2.

**Rule-based baseline — iterative refinement.** The deployed rule-based policy (`group_approach_baseline_node`) implements the geometric rule established in Section 3.3 — approach along the robot-to-centroid line, stop short by a standoff distance, face the centroid — but its live deployment required several rounds of empirically-driven correction beyond the initial design, each worth reporting as part of the methodology rather than treated as mere bug-fixing, since each correction is itself a measured methodological finding:

1. **Standoff distance**, defaulted to 1.2 m, is deliberately set to Hall's proxemics boundary between personal and social space (a defensible, citable, and independently parameterised default; see Helbing and Molnár, 1995 for the same social-distance principle formalised as a force model).
2. **Goal throttling** was added after early runs revealed that publishing a fresh navigation goal on every perception frame caused Nav2 to continuously preempt and restart planning, so the robot barely moved — a new goal is now only issued if the target has moved by more than 0.40 m or the previous goal has finished.
3. **Per-person clearance, not just centroid standoff**, was added after a live run measured an actual O-space intrusion at 0.43 m from the nearest person — inside Hall's intimate distance — despite satisfying the centroid-based standoff, because the centroid itself shifts when only part of a group is visible to the camera. The chosen pose is now checked against **every** individually detected person and pushed back along the approach line until clear of all of them, with the clearance target set to 0.7 m to the *nearest person* rather than to the group centre — chosen specifically because this group's measured O-space radius (~0.71 m) meant a 0.7 m centroid-based standoff would have placed the robot inside the conversation, whereas 0.7 m to the nearest person sits inside Hall's personal zone (0.45–1.2 m), which HRI approach studies typically report as comfortable for a service robot initiating contact, without being intimately close.
4. **Body radii, not centre-to-centre distance**, were added after a further live failure: treating clearance as a distance between point centres, rather than between TIAGo's physical footprint (~0.30 m radius) and a person's body (~0.25 m radius), left only 0.15 m of true physical gap at a nominal 0.7 m setting — the robot wedged itself into a group, came within 0.062 m of a person, and then remained stationary for 84% of a ten-minute run because Nav2 could find no admissible path out. Both radii are now added explicitly to the requested clearance, so a requested 0.7 m is a *delivered* 0.7 m of actual physical gap.
5. **Gap-based approach selection** (the current default, `approach_mode: gap`) evaluates candidate standoff angles around the group and selects one with at least a 60° clear arc, rather than assuming the direct robot-to-centroid line is itself unobstructed.
6. **Stuck detection and an "unwedge" reflex** were added as a final safety net: if the robot has not moved by more than 0.10 m for 25 seconds, and 30 seconds have elapsed, it reverses directly at −0.15 m/s for 3 seconds before retrying — a reactive recovery behaviour for the case where Nav2's own planner cannot find a way out unassisted.

**Multi-group patrol mission.** For the live experiment, TIAGo executes a fixed, repeatable five-waypoint patrol route (`mission_node`) rather than free exploration, so that every trial — under either policy — covers the same ground in the same order, meaning any behavioural difference reflects the policy rather than which corner of the world the robot happened to visit. The mission pauses at each detected group to allow the active approach policy to attempt an approach (bounded by a 90-second safety ceiling, resolved earlier by an event-driven "approach complete" signal from the policy itself in the common case), dwells briefly (8 seconds) once an approach succeeds before resuming, retries a blocked waypoint for up to three attempts to tolerate a temporarily obstructing person rather than treating one as a permanent obstacle, and "retires" a group after three failed approach attempts so a single unreachable group cannot stall the entire mission indefinitely.

### 3.6 Evaluation metrics

The proposal specifies eight evaluation metrics, which split cleanly into two groups by what they require, and this project's methodology treats that split explicitly rather than blurring it. **Measurable offline**, from the recorded demonstration data alone: approach-position error (Objective 4 threshold <0.4 m) and approach-orientation error (<20°), since the demonstrated stop pose is recoverable from the robot's own recorded odometry and each policy predicts a pose in the same frame. **Measurable only in the running simulation**: O-space intrusion (whether the robot's physical footprint, not merely its centre point, overlaps the O-space circle), minimum distance to any person, and group cut-through rate (whether the path crosses between two members of the same group — geometrically distinct from intrusion) all require group positions in real metres, which the recorded, uncalibrated video cannot provide; collision-free rate, task success rate, path length, and navigation time are properties of an executed trajectory and have no offline equivalent at all. All six simulation-only metrics are scored against the world's **true, ground-truth person positions** rather than the robot's own detections — a deliberate methodological choice, since scoring against detections would let a perception failure flatter the result (a robot that never sees a group cannot be measured intruding on it, and would appear to score perfectly), whereas scoring against ground truth measures the *behaviour* itself and keeps perception failures and behavioural failures analytically separable in the results. Task success itself required its own re-calibration once the gap-based approach policy (Section 3.5) changed what "correctly positioned" means: the acceptable distance-to-group-centre band was widened at its lower bound from 0.8 m to 0.5 m, because a robot now correctly standing in a tight group's P-space at 0.7 m of person-clearance can legitimately sit well inside 0.8 m of the group's centre — the original band would have scored a correct approach as a failure.

### 3.8 Critical discussion of the chosen methodology

Several methodological choices in this project trade rigour in one dimension for feasibility in another, and a Masters-level treatment requires naming the trade rather than only the outcome. The decision to evaluate exclusively via quantitative geometric metrics, with no qualitative user study, sacrifices any direct measurement of perceived comfort or naturalness in exchange for a comparison that is safe, repeatable, and achievable within the project's timeframe — a defensible choice given the ethical and time constraints already discussed, but one that limits every conclusion in Chapter 5 to "geometrically closer to the human demonstration" rather than "more socially acceptable to a bystander," and these are not proven to be the same thing. The decision to train via plain offline Behavioural Cloning, with no DAgger-style (Ross, Gordon and Bagnell, 2011) online correction against the learner's own visited states, accepts a known, named risk of compounding error under distributional shift, in exchange for a training procedure that does not require an interactive expert available during training — appropriate given that the "expert" here is 24 already-recorded, non-expert demonstration sessions rather than a supervisor who could be queried live. The re-specification of the O-space validation criterion from an unmeasurable metric distance to a measurable proportion of person-width (Section 3.3) preserves the original criterion's intent and order of magnitude, but is a genuine adaptation to a data limitation discovered during the project rather than a pre-registered method, and is disclosed as such rather than presented as the original plan. Finally, the `group_scale_norm` feature used by the Behavioural Cloning model was defined during offline training as a pixel-based apparent-size proxy for distance (mean bounding-box width over image width), and the live policy node must *reconstruct* an equivalent value from true simulated depth at deployment time, since no such pixel proxy exists once real metric distance is available — this is a genuine train/deployment domain shift, reported here as a limitation rather than resolved, since retraining the model directly on metric features was judged out of scope given the project's remaining time.
