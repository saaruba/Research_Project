## 4. Implementation

### 4.0 Overview of the software artefact

This project's primary output is a working software system, not solely a trained model: three ROS 2 packages, a 24-session dataset-processing pipeline, four trained model artefacts, and a live Gazebo/Nav2 simulation, all in a single version-controlled repository (`github.com/saaruba/Research_Project`, 38 commits at time of writing). By line count alone, the codebase comprises **9,446 lines of Python** across the offline processing pipeline (`scripts/`, 44 Python and shell scripts) and the two custom ROS 2 packages' node code (`src/tiago_group_approach`, `src/tiago_head_control`) — excluding the dataset itself, trained model files, and the third-party TIAGo/Nav2/Gazebo packages the system depends on but did not author. This is worth stating explicitly in the dissertation as the scale of the "significant software artefact" the brief asks Masters projects to identify, distinct from the ML model or the dataset analysis, which are reported separately below. All source code referenced in this chapter is uploaded to the module's Supporting Documentation area per the assessment brief, not reproduced here in full.

### 4.1 Software development projects

#### 4.1.1 Toolsets and machine environments

Development took place inside a VS Code Dev Container ("CMP9764 Teaching Devcontainer", image `ghcr.io/athapoly/cmp9764_dock:latest`), running ROS 2 Humble on Ubuntu, with a browser-accessible VNC desktop (noVNC on port 5801, proxying an internal TigerVNC session on an Xvfb virtual framebuffer) as the mechanism for viewing Gazebo/RViz output from a container with no local display. The container's `postStartCommand` runs `.devcontainer/post-create.sh` on every start, which sources the ROS 2 and MoveIt workspace setup files, runs `colcon build --symlink-install --continue-on-error`, and (re)starts the VNC/desktop stack — meaning the simulation toolchain is **re-provisioned automatically on every container rebuild** rather than relying on manual setup surviving between sessions, a design forced by a real incident (Section 4.1.1, environment fragility, below).

Three separate `pip` requirements files were deliberately maintained rather than one, each pinned to exact versions for reproducibility (numpy 2.2.6, pandas 2.3.3, scikit-learn 1.7.2, joblib 1.5.3, opencv-python-headless 4.13.0.92, rosbags 0.11.3, Pillow 12.2.0, ultralytics ≥8.3,<9), with the split itself a considered design decision rather than an accident: `requirements.txt` for the full offline data pipeline (needs the raw PLUS-HRI dataset), `requirements-simulation.txt` for a machine that only runs the live experiment (a strict subset — no `rosbags`, since no bag file is ever read at simulation time), and `requirements-locateanything.txt` isolated into its own virtual environment entirely, because LocateAnything-3B pins `numpy==1.25.0` while the rest of the pipeline requires numpy 2.x for pandas/scikit-learn compatibility — installing both in one environment was tried and found to break the whole pipeline with ABI errors, which is why the requirements files themselves now carry an explicit warning against it. ROS 2 message packages (`rclpy`, `nav2_msgs`, `tf2_ros`, `geometry_msgs`, `sensor_msgs`, `gazebo_ros`, and others) are deliberately excluded from all three `pip` files, since they are not distributed on PyPI at all and are only satisfiable from the ROS 2 Humble system installation, built via `colcon` rather than `pip`.

**Environment fragility, and the engineering response to it.** Several real, time-costly environment failures shaped the toolchain's current design, and are worth reporting as implementation history rather than only as a "lessons learned" footnote, since each directly produced a script or safeguard still in the repository. The devcontainer was found, partway through the project, to have been silently recreated (its hostname changed), which destroyed everything installed inside the container but outside the `/workspaces` mount, including an entire prior TIAGo/Nav2 installation — `scripts/check_sim_setup.sh` was written specifically to re-establish ground truth about what is actually installed, rather than trusting prior setup documentation, and `scripts/install_sim_stack.sh` is now idempotent and re-run from `post-create.sh` on every start for exactly this reason. Separately, `python3 -m venv` was found not to work in this container at all (`python3.10-venv` is not installed by default), which silently corrupted the main pipeline's numpy version once before the fault was understood (a failed venv creation does not stop the shell script, so the subsequent `pip install` landed in the wrong environment); `scripts/setup_locateanything.sh` now explicitly verifies `which python3` resolves inside the intended virtual environment and hard-aborts otherwise, and carries a `--repair` mode to reinstall the correct numpy/pandas/scikit-learn versions if it happens again. Installing `ultralytics` was also found to silently break `colcon build` afterward (it pulls a modern `setuptools` incompatible with `colcon-core`'s expectations), fixed by explicitly pinning `packaging>=24.0` and `setuptools<80` immediately after any ultralytics install. Finally, `colcon build`'s package discovery was found to crawl into the 67 GB `dataset/` and 7.8 GB `models/` directories and misidentify numpy internals as ROS packages, producing hundreds of spurious errors before reaching the real packages — resolved with `COLCON_IGNORE` marker files in `dataset/`, `models/`, and `la3b_env/`.

The LocateAnything-3B comparison additionally required access to a separate GPU-equipped machine (documented in `docs/LAB_PC_SETUP.md`), since the model's PyTorch/transformers/decord dependency stack is GPU-oriented and impractical to run purely on the devcontainer's CPU allocation; the comparison frames were exported on the devcontainer, transferred, run there, and the results transferred back — a manual, one-off transfer process (`scripts/make_transfer_bundle.sh`) rather than a persistent dual-machine pipeline, appropriate given it needed to run only once.

#### 4.1.2 Design

**Package architecture.** The system is organised as three ROS 2 packages, each with a distinct, single responsibility:

- **`tiago_group_approach`** (`ament_python` build) — the project's own contribution: perception, both policies, localisation, mission control, and evaluation. Declares its ROS 2 dependencies explicitly in `package.xml` (`rclpy`, `geometry_msgs`, `nav2_msgs`, `tf2_ros`, `tf2_geometry_msgs`, `sensor_msgs`, `std_msgs`, `visualization_msgs`, `message_filters`, `launch`, `launch_ros`) and notably **deliberately excludes `cv_bridge`** — the standard ROS image-conversion library — because its compiled C++ extension is built against numpy 1.x and was found to break under this workspace's numpy 2.x requirement; image conversion between ROS `sensor_msgs/Image` messages and numpy arrays is instead implemented manually (`group_perception_node.imgmsg_to_array()`), a small but deliberate piece of custom code written specifically to route around a dependency conflict rather than an oversight.
- **`tiago_head_control`** — an earlier, simpler package (a basic head pan/tilt scan node, `head_scan_node.py`), predating the main group-approach system, retained as the project's first working ROS 2 node and its only package carrying the standard ROS 2 ament lint test scaffold (`test_copyright.py`, `test_flake8.py`, `test_pep257.py` — style/licence-header checks generated by the package template, not functional tests).
- **`tiago_social_worlds`** (`ament_cmake` build, mixing compiled-package conventions with pure Python launch files and static assets) — the simulation environments themselves: hand-built and generated Gazebo world files, occupancy-grid maps derived from world geometry, ground-truth JSON files, and their launch files.

**Node graph.** `tiago_group_approach` exposes seven runnable nodes via `setup.py`'s `console_scripts` entry points, each independently launchable and each with one clearly stated job: `group_perception_node` (camera + depth → `/group_centroid` in the map frame), two **drop-in-swappable** policy nodes that both consume `/group_centroid` and both emit a `NavigateToPose` goal — `group_approach_baseline_node` (the geometric rule) and `bc_policy_node` (the trained model) — `gt_localisation_node` (continuous map→odom from Gazebo ground truth), `explore_node` (a room-patrol behaviour so the camera encounters people at all), `mission_node` (the scripted multi-waypoint tour that drives the actual timed experiment and signals when to stop), and `metrics_recorder_node` (scores and writes one JSON result file per run). `launch/group_approach.launch.py` wires the whole graph together behind a single `policy:=rule|bc` launch argument, which is the literal mechanism realising Objective 4's controlled comparison: changing one launch argument, with every other node and topic identical, is what makes the two policies comparable.

**Data schemas, as actually implemented.** Rather than an ad-hoc set of intermediate files, the pipeline's stages are connected by consistently-shaped CSVs, each with a fixed column contract downstream code depends on: `detected_people.csv`/`detected_people_individual.csv` (per-frame, per-person pixel bounding boxes from YOLOv8n or LocateAnything-3B); `detected_groups.csv` (per-frame, per-group: `group_id`, `num_people`, `member_indices`, `group_center_x/y`, bounding extent, `avg_bbox_width`, `is_largest_group`, and, once `estimate_approach_points.py` has run, `approach_x/y` and `approach_facing_deg`); `approach_pose_dataset.csv` (the final Behavioural Cloning training table: the seven input features plus `target_dx/dy/dyaw`, one row per timestamp inside an inferred approach-lead-up segment); and `train_table.csv`/`val_table.csv`/`test_table.csv` (the session-level split, read directly by `train_approach_pose_model.py`, `train_approach_pose_mlp.py`, and `grid_search_approach_pose.py` alike, so all three scripts are guaranteed to use an identical split rather than three independently-computed ones).

**Iterative design history, as a prototyping record.** Several components were rebuilt through multiple concrete versions rather than arriving at their final form directly, and this history is itself evidence of an iterative, evaluation-driven design process worth presenting as such: the Behavioural Cloning target evolved from an initial raw-`cmd_vel` regression (`train_baseline_model.py`) to a richer version adding raw human-position features (`train_social_baseline_model.py`, found to perform *worse*) to the final relative approach-pose target (`build_approach_pose_dataset.py`/`train_approach_pose_model.py`); its input features evolved from raw normalised pixel position to a physically-meaningful bearing angle; and the live rule-based policy went through the six-stage refinement documented in Methodology Section 3.5 (standoff-only → goal-throttled → per-person-clearance → body-radius-corrected → gap-based → stuck-recovery-equipped), each stage a distinct, git-committed version rather than a single final design.

#### 4.1.3 Testing

Testing in this project is predominantly **empirical and system-level** rather than unit-test-driven, a methodological choice worth naming honestly rather than implying more conventional software-engineering test coverage than exists: `tiago_group_approach`'s `setup.py` declares a `pytest` test extra, but no `test/` directory or actual test file exists in that package, so no automated unit tests were written for the project's own nodes — only the older, simpler `tiago_head_control` package carries the ROS 2 ament template's standard style/licence-header checks (`ament_copyright`, `ament_flake8`, `ament_pep257`), which verify code style rather than behaviour. This is an accepted trade-off given the project's timeframe and the nature of most of its logic (ROS callbacks driving a physics simulation, which is awkward to unit-test in isolation), and is compensated for by three other, more suited layers of validation actually built and used:

1. **Data/model validation with held-out ground truth** — the closest equivalent to unit testing this project has, and arguably more rigorous for this domain: `validate_detector_recall.py` checks the deployed YOLOv8n detector against real, independent ground-truth annotations (sessions 1 and 3) rather than merely asserting it should work; `evaluate_approach_pose.py` and the grid-search script evaluate every trained model against a test split it never influenced training or tuning decisions on; `validate_ospace_estimate.py` was itself "tested end-to-end with synthetic labels" (per its own docstring) before ever being pointed at real hand-labelled data, to confirm the scoring logic was correct independent of the labelling task.
2. **System diagnostics as integration tests** — `scripts/check_sim_setup.sh` and `scripts/preflight_check.sh` are, in effect, ordered integration-test suites for the live system: the former establishes exactly what is and is not installed in the container (rather than trusting documentation), and the latter checks every link in the perception → policy → Nav2 chain in dependency order against an already-running simulation (environment/venv correctness, ROS sourcing, `ultralytics` import, simulation topics *and* that the camera is actually streaming rather than merely advertised, the Nav2 action server, the map→base_footprint transform, this project's own nodes, and whether `/group_centroid` is actually publishing) — designed explicitly so that "the robot isn't moving" can be diagnosed top-down to its first genuine failure rather than guessed at.
3. **Resumable, checkpointed execution as a testing safeguard** — `grid_search_approach_pose.py` checkpoints its results after every configuration and skips any already present on restart, which functions as a practical safeguard against a long-running process being interrupted and silently producing partial or duplicated results; the same checkpoint file (`grid_search_results.csv`) also served as a direct, inspectable record confirming the search had actually explored the intended parameter space rather than silently short-circuiting.

Live-simulation "testing" in the conventional sense took the form of the run-diagnosis cycle documented in Methodology Section 3.5: a run's own recorded metrics (task-success reason, collision flags, minimum person distance) were used to diagnose specific implementation faults — the 0.43 m O-space intrusion, the 0.062 m near-miss, the 84%-stationary run — each of which drove a specific, identifiable code change, making the simulation's own metrics output a de facto regression-testing signal across successive versions of the rule-based node.

### 4.2 Research projects (not involving human participants)

#### 4.2.1 Dataset acquisition and annotation

The PLUS-HRI dataset (24 sessions) was not collected by this project but is processed and annotated by it in full, since it arrives with no group, O-space, or (for 22 of 24 sessions) even person-position labels. Acquisition and annotation is implemented as a five-stage script pipeline, each stage's output consumed by the next and each independently re-runnable per session:

1. **Session inspection and cataloguing** (`inspect_dataset_session.py`, `build_master_session_summary.py`) — established, by direct inspection rather than assumption, which files and topics exist in each of the 24 sessions, surfacing the two-generation split described in Methodology 3.1.
2. **Extraction from ROS 1 bags** (`extract_training_table.py`) — reads each session's bag using the `rosbags` library's ROS 1 reader and the `ROS1_NOETIC` typestore (a fix for an initial typestore mismatch), merging pose, LiDAR, and (where available) face-landmark topics onto a common timeline via `pandas.merge_asof` with the tolerances described in Methodology 3.1.
3. **Person detection for the 22 sessions without face annotations** (`extract_person_detections.py`) — runs YOLOv8n over each session's video, reading frames strictly sequentially (avoiding the corrupt-frame bug described in Methodology 3.1) rather than seeking, and writes per-frame, per-person bounding boxes.
4. **Readiness checking and combination** (`check_dataset_readiness.py`) — validates and concatenates all 24 sessions' extracted tables into `combined_training_table.csv` before splitting.
5. **Session-level splitting** (`split_dataset.py`) — the train/val/test assignment described in Methodology 3.1, implemented with a fixed seed (42) for reproducibility and sessions 1/3 forced into train.

Group and O-space annotation — since none exists in the source dataset at all — is itself an implemented pipeline stage rather than a pre-existing label: `cluster_groups.py` (connected-components clustering on a bbox-width-normalised similarity graph, Methodology 3.3) and `estimate_approach_points.py` (the geometric approach-point rule) together constitute the project's own annotation process, run identically across all 24 sessions to produce `detected_groups.csv` per session. The O-space hand-labelled validation set (`prepare_ospace_validation.py`, 30 frames across 18 sessions) is a second, independent annotation effort layered on top, created specifically to check the automated annotation's own accuracy.

#### 4.2.2 Algorithm/model design and selection

**Group clustering algorithm.** Implemented as a per-frame similarity graph over detected people, where an edge is added between two people if their pixel distance is below `GROUP_DISTANCE_THRESHOLD` × their average bounding-box width; connected components of that graph are then read off directly as candidate groups (including singleton "groups" of one, retained rather than discarded so downstream code can distinguish "no one here" from "one person alone"). This is a deliberately simple, non-learned geometric algorithm, chosen because — as established in Methodology 3.3 — Vascon *et al.*'s (2016) result that F-formation structure is recoverable from position alone (without orientation) justifies a lightweight clustering approach over a more complex learned or orientation-dependent alternative that this dataset could not have supplied ground truth for regardless.

**Approach-point geometry.** A single, reused geometric rule computes a standoff point for a given group centroid and (assumed or actual) robot viewpoint: draw a line from viewpoint through centroid, place the target point a fixed distance outside the group's extent along that line, oriented to face back toward the centroid. This exact rule is implemented twice with different coordinate inputs — once in pixel space for the recorded-dataset annotation (`estimate_approach_points.py`), and once in real map-frame metres for the live baseline policy (`group_approach_baseline_node.py`) — a deliberate reuse of one algorithmic idea across two different data regimes, rather than two unrelated implementations, which is itself worth stating plainly as a design choice.

**Rule-based policy as a small state machine.** `group_approach_baseline_node`, in its current (gap-based) form, implements considerably more than the geometric rule alone; it is best described as a state machine layered on top of it: (1) receive a group centroid and the current list of individually detected people; (2) compute candidate standoff angles around the group and select one offering at least a 60° clear arc (`min_gap_deg`); (3) check the candidate pose against every detected person's body radius plus the robot's own footprint radius, pushing the point outward until `min_person_clearance` (0.8 m) of true physical gap is achieved from the nearest person; (4) throttle goal (re-)issuance so a new `NavigateToPose` goal is only sent if the target has moved more than `goal_update_threshold_m` (0.40 m) or the previous goal has completed, preventing continuous plan-preemption; (5) monitor robot displacement over a rolling window, and if it falls below `stuck_move_threshold_m` (0.10 m) for `stuck_timeout_s` (25 s) after an `unwedge_after_s` (30 s) grace period, execute a 3-second reverse manoeuvre at `unwedge_speed` (−0.15 m/s) before retrying; and (6) track which groups have already been attempted (`group_memory_radius` 1.5 m) and "retire" a group after `max_attempts_per_group` (3) failures, so a single unreachable group cannot stall the mission. Every numeric threshold here is a ROS 2 parameter, not a hard-coded constant, so it can be cited and justified individually in the dissertation without a code change — this was a deliberate design decision from the node's first version onward.

**Learned policy implementation.** Both trained model families are implemented via scikit-learn, wrapped in a `Pipeline` with a `StandardScaler` preceding the estimator for the MLP (MLPs are scale-sensitive; Random Forest is not, and is trained without the scaling step) — `MLPRegressor` and `RandomForestRegressor` respectively, both natively supporting the three-dimensional (Δx, Δy, Δyaw) regression target directly rather than requiring three separate single-output models. Trained models are serialised with `joblib` and loaded at runtime by `bc_policy_node`, which reconstructs the exact seven-feature vector documented in Methodology 3.4 in a fixed, explicit order (a deliberate design choice: the node's own docstring notes that a silent feature-order mismatch would produce garbage predictions with no error raised, so the assembly code is written to make the order impossible to miss on inspection) and converts the model's relative-frame prediction into an absolute map-frame Nav2 goal using the robot's current TF pose at prediction time.

**Scripted mission algorithm.** `mission_node` drives a fixed five-waypoint tour (coordinates hard-coded as a launch parameter default, overridable), advancing to the next waypoint on successful arrival, retrying a blocked waypoint after a 15-second wait (tolerating a temporarily obstructing person) for up to three attempts before treating it as genuinely unreachable, and yielding control to whichever approach policy is active whenever a group is sighted — implemented as an explicit two-topic handshake (`/approach/start`, `/approach/complete`) rather than a shared state variable, specifically because the mission node must actively cancel its own in-flight Nav2 goal before the policy node sends its own, or the two nodes preempt each other's goals and the robot never completes either.

#### 4.2.3 Parameter tuning

Hyper-parameter tuning (`grid_search_approach_pose.py`) was implemented as an exhaustive grid search over two independent parameter spaces, one per model family, each candidate scored only on the validation split (Methodology 3.4). The full grids actually searched were: for Random Forest, `n_estimators ∈ {100, 300}` × `max_depth ∈ {6, 10, 14, 20, None}` × `min_samples_leaf ∈ {1, 5, 20, 50}` (40 configurations); for the MLP, `hidden_layer_sizes ∈ {(128,64), (64,32), (32,16), (256,128)}` × `alpha ∈ {1e-4, 1e-3, 1e-2, 1e-1}` (16 configurations) — 56 total configurations across both families. A `--quick` mode with a deliberately smaller grid (6 Random Forest and 4 MLP configurations) is also implemented, intended for fast iteration/debugging of the search script itself rather than for producing the reported results. Selection ranked every candidate purely by mean validation-set position error (Euclidean distance in the predicted (Δx, Δy) plane) — the quantity Objective 4 sets a numeric threshold on — with orientation error recorded but explicitly not used for ranking, since a model that predicts orientation accurately while stopping in the wrong place does not solve the actual task. The search is checkpointed to `grid_search_results.csv` after every configuration, both for practical resumability given the runtime of 56 model fits and as a testing safeguard (Section 4.1.3).

#### 4.2.4 Performance metrics implementation

The two offline metrics (Methodology 3.4/3.6) are implemented directly as vectorised numpy operations in `evaluate_approach_pose.py`: position error as the Euclidean distance between predicted and demonstrated (Δx, Δy), and orientation error as the absolute angular difference between predicted and demonstrated Δyaw, wrapped correctly into the [−π, π] range before conversion to degrees (`wrap_angle`, reused identically in the grid-search script to guarantee the two report the same numbers for the same model).

The six simulation-only metrics are implemented in `metrics_recorder_node`, sampling at a fixed `sample_rate_hz` (10 Hz) throughout a run: collision-free rate is derived from the live `/scan_raw` LiDAR topic, flagging a collision when the minimum valid return falls below `collision_distance_m` (0.30 m), with returns below `min_valid_range_m` (0.20 m) excluded as the robot detecting its own chassis rather than an obstacle, and a `collision_grace_s` (5 s) window at the start of each run excluded entirely to avoid false positives while the robot is still settling after spawn. Task success is scored against a distance-to-group-centre band recalibrated during development (Methodology 3.6) to a lower bound of 0.5 m (from an original 0.8 m), specifically because the current gap-based approach policy legitimately stands closer to a tight group's true centre than the older centroid-standoff policy did. O-space intrusion, minimum distance to any person, and group cut-through rate are all computed against each world's `.groundtruth.json` file of true person positions in real metres (Methodology 3.5/3.6) rather than the robot's own perception output, specifically so a perception failure cannot be scored as a behavioural success. Every run — regardless of outcome — writes exactly one JSON result file (policy name, timestamp, full sampled trajectory, and every computed metric) to `dataset/processed/sim_results/`, which `summarise_sim_results.py` later aggregates across multiple runs into the rule-vs-BC comparison table for Chapter 5, deliberately reporting raw counts (e.g. "8/10") alongside percentages so that a small number of trials cannot present itself as more statistically solid than it is.
