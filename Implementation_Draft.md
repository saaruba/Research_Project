## 0. The project's own phase-naming scheme

Nearly every script and node docstring in this codebase tags itself with a letter — "Phase C, step 1", "Phase F: train the actual approach-pose model" — and this is a real, deliberate organisational scheme carried from `TIAGo_Project_Master_Checklist.md`, not incidental labelling. It's worth documenting explicitly here since it's the actual mental model the codebase was built around, and every section below can be read against it:

- **Phase A** — Dataset & extraction pipeline (Section 7.1 below).
- **Phase B** — Person perception, Objective 2 (completed 6 Aug 2026; Section 7.6).
- **Phase C** — Group detection / F-formation / O-space, Objective 3, offline half (`cluster_groups.py`, `estimate_approach_points.py`; explicitly scoped in its own docstrings as 2D image-pixel-only, with a note that the live Nav2 baseline in Phase E needs "the same formula re-applied to real-world (x, y) positions... not these pixel values directly").
- **Phase D** — Simulation environment. The master checklist records a genuinely important early blocker here: Nav2 was, for a period, never actually confirmed working because it had never been installed at all — "the blocker behind 6 of the 8 evaluation metrics and all of Phase G was a missing dependency, not a configuration problem," a fact worth keeping as an honest account of how much early progress was blocked by one uninstalled package rather than a design flaw.
- **Phase E** — Rule-based baseline, Objective 4, built deliberately *before* the ML model specifically to prove the pipeline shape end-to-end and give Phase F something concrete to be compared against (Section 3.2 above).
- **Phase F** — the Behavioural Cloning model, Objective 4. The checklist preserves an early, honestly-reported negative-ish result from the very first trained model (6 Aug): test-set forward-distance barely beat the naive baseline, lateral distance and orientation did not beat it at all, attributed even then to "only 8 input features may not carry enough signal" and "462 independent approach events" being a much smaller true sample than the 70k-row count suggests — i.e. the label-ambiguity/sample-size diagnosis that the full v2 study (Methodology Section 3.5) later investigated exhaustively was already suspected in the project's own working notes from very early on, not discovered only in the final week.
- **Phase G** — Integration: turning the offline Phase C/E/F components into the live, closed-loop robot system (Section 3 above, in full).
- **Phase H** — Evaluation: the full live comparison (Section 7.9 below; Methodology Sections 3.6–3.7).

## 2. Development environment and tooling

The project runs inside a VS Code Dev Container, `ghcr.io/athapoly/cmp9764_dock:latest` ("CMP9764 Teaching Devcontainer"), ROS 2 Humble on Ubuntu, running as user `lcas`. The devcontainer config (`.devcontainer/devcontainer.json`) declares 2 CPUs / 8 GB memory as a minimum host requirement and an *optional* GPU — meaning the container itself does not assume GPU access, which is directly why LocateAnything-3B benchmarking had to be done on a separate lab PC/workstation with an actual NVIDIA GPU rather than inside this container.

`.devcontainer/post-create.sh` is the container's bring-up script, and it is doing a surprising amount of work beyond a normal `colcon build`: it sources ROS 2 Humble and a MoveIt workspace, runs `colcon build --symlink-install --continue-on-error` (tolerating individual package build failures rather than aborting the whole build), then sets up a full virtual desktop so the simulation's GUI (Gazebo, RViz) can be viewed in a browser — cleaning up stale X11/VNC lock files, starting `dbus`, launching `Xvfb` (a virtual framebuffer at 1920×1080×24), starting XFCE as the `lcas` user, running TigerVNC on port 5901, and finally piping that through a noVNC websocket proxy on port 5801 (the port the devcontainer forwards and auto-opens in a browser tab). This whole VNC/noVNC chain exists because the devcontainer has no physical display, and Gazebo needs one to render.

Two diagnostic shell scripts exist specifically to answer "why isn't this working" without re-deriving the answer from scratch each time: `scripts/check_sim_setup.sh` audits what's actually installed in the container versus what the project needs (noting explicitly that the devcontainer was recreated at least once during the project, and anything installed outside `/workspaces` does not survive that), and `scripts/preflight_check.sh` walks the entire chain of things that must be true for the robot to actually drive to a group — checking each link in order on the principle that "the first FAIL is your problem; later failures are often just consequences of it."

## 3. The `tiago_group_approach` package — the live system

This is the project's main package, an `ament_python`-built ROS 2 package with 7 executable nodes declared as `console_scripts` in `setup.py`. `cv_bridge` is deliberately never used anywhere in this package — its compiled extension links against numpy 1.x and breaks under the numpy 2.x this workspace requires — so every image is converted manually via a hand-written `imgmsg_to_array()` function instead of the usual ROS convenience library. This is stated directly as an inline comment in both `package.xml` and the perception node itself, since it's exactly the kind of non-obvious workaround a marker or future maintainer would otherwise have to rediscover by debugging an import error.

Package dependencies (`package.xml`): `rclpy`, `geometry_msgs`, `nav2_msgs`, `tf2_ros`, `tf2_geometry_msgs`, `builtin_interfaces`, `sensor_msgs`, `std_msgs`, `visualization_msgs`, `message_filters`, `launch`, `launch_ros`. Test dependencies are declared (`ament_copyright`, `ament_flake8`, `ament_pep257`, `python3-pytest`) but — stated honestly rather than glossed over — **no actual unit tests exist for this package's own node logic**, despite the `pytest` extra being declared in `setup.py`. See Section 7 for how this gap is actually compensated for in practice.

### 3.1 `group_perception_node.py` (944 lines) — the perception pipeline

The single largest and most consequential node in the system. Its own docstring states the point plainly: every earlier phase's perception was constrained to 2D image pixels because the recorded PLUS-HRI video has no depth or calibration, and this node is "where the project stops being an offline data-analysis exercise and becomes a robot system," because it has access to a *real* depth image and *real* `CameraInfo`, so every downstream quantity (group centroid, O-space, the metrics in Chapter 3 Section 3.7) becomes a genuine metric position rather than a pixel-space proxy.

**Topics.** Subscribes to `~/rgb` (`sensor_msgs/Image`, default `/head_front_camera/rgb/image_raw`), `~/depth` (`sensor_msgs/Image`, default `/head_front_camera/depth/image_raw`), `~/camera_info` (`sensor_msgs/CameraInfo`). Publishes `/group_centroid` (`geometry_msgs/PointStamped`, map frame — what both policy nodes actually consume), `/detected_people` (`geometry_msgs/PoseArray`, map frame, every individual person, for debugging/RViz), and `/group_markers` (`visualization_msgs/MarkerArray`, the RViz overlay).

**Functions and structure** (from the actual class/function definitions): a module-level `imgmsg_to_array()` helper (the manual `cv_bridge` replacement); the `GroupPerceptionNode` class with `__init__`, `trigger_callback`, `_infer_worker` (runs detector inference on a background thread — necessary once LocateAnything-3B's multi-second latency entered the picture, so a slow inference doesn't block the ROS executor), `periodic_step` (drives the "periodic" detection mode described below), `check_service` (polls whether the LocateAnything HTTP service is actually up before trying to use it), `detect_people_boxes` (dispatches to whichever detector backend is configured), `camera_info_callback`, `depth_to_metres`, `person_depth`, `backproject` (the pinhole camera back-projection: `x=(u−cx)d/fx, y=(v−cy)d/fy, z=d`), `cluster_people` (connected-components clustering in true metres, 1.5 m single-linkage threshold — the live counterpart to the offline `cluster_groups.py`'s pixel-normalised version), `image_callback` (the main per-frame pipeline, by far the largest single method in the node), `publish_debug_image`, `publish_people`, and `publish_markers`.

**Detector backends, and the operational modes this node supports.** The `detector` parameter selects `yolo` (default, YOLOv8n, ~0.005 s/frame) or `locateanything` (NVIDIA LocateAnything-3B via the separate HTTP service). Beyond the simple on/off of which detector runs, the node supports three distinct **timing modes** via the `oneshot` parameter, which the launch file exposes as `'auto' | 'true' | 'false' | 'periodic'`: `auto` keeps the historically shipped behaviour (continuous detection for YOLO, one-shot for LocateAnything); `periodic` re-triggers inference every `retrigger_period_s` seconds using the threaded `_infer_worker`, which is what a genuine LocateAnything-vs-YOLO *policy* comparison actually needs, since a pure one-shot mode gives an entire trial only a single detection and can't meaningfully drive a closed-loop policy at all. This periodic mode is a direct engineering response to the finding (Methodology Section 3.2.3) that a single detection per trial makes the three policies statistically indistinguishable — periodic mode is the node-level mechanism that made a *fairer*, if still heavily constrained, LocateAnything condition possible for the final 60-trial batch.

An `edge_margin_px` parameter (default 8) rejects any detected person bounding box within that many pixels of the image border, on the reasoning that a partially-visible person at the frame edge has an unreliable centroid; setting it to 0 disables the filter. A `confidence` parameter (default 0.45, raised from an earlier, more permissive 0.4) is the YOLO detection threshold — the docstring notes explicitly that 0.4 was found to accept furniture and wall-edge textures as people in the synthetic Gazebo scene, which becomes a serious problem specifically when `min_group_size=1`, since a single false positive is then enough to send the robot off to "approach" nothing.

### 3.2 `group_approach_baseline_node.py` (749 lines) — the rule-based policy

The hand-engineered geometric baseline, and the single largest policy node — its size reflects the six rounds of iterative, empirically-driven refinement documented in Methodology Section 3.6.4, all of which live in this one file. Core rule, stated in the module docstring: get the robot's position from TF (`map → base_link`), get a detected group centroid from `/group_centroid`, draw a line from robot to centroid, place the goal `standoff_distance` metres short of the centroid along that line (Hall's proxemics personal/social boundary, 1.2 m default, exposed as a ROS parameter specifically so it can be tuned and justified without a code change), facing back toward the group.

**Functions**: `__init__`, `group_key` and `group_finished` (the 1.5 m-cell group-memory system from fault 5.14 — remembering which groups have already been attempted), `retire_group`, `group_is_moving`, `effective_clearance`, `check_stuck` (the stuck-detection half of the "unwedge" reflex), `gap_approach_pose` (containing a nested `angdiff` helper — the gap-based approach-point selection from Methodology Section 3.6.4 item 5: evaluates candidate standoff angles and picks the nearest one with at least a 60° clear arc), `people_callback`, `get_robot_position`, `compute_approach_pose` (the largest single method — combines standoff, per-person clearance with body radii, and gap selection into one final goal pose), `group_centroid_callback`, `send_nav_goal`, `goal_response_callback`, `result_callback`, `scan_callback`, `rear_is_clear` (checks the rear laser beams before allowing a reverse manoeuvre — the fix for fault 5.15, where blind reversal drove the robot into furniture it couldn't see), `unwedge_tick` (the actual reverse-and-retry recovery behaviour), and `dwell_tick` (the 6 s post-arrival dwell from fault 5.13).

A worked manual test procedure is documented directly in the docstring: publish a single `/group_centroid` message at map `(2.0, 1.0)` via `ros2 topic pub --once`, and the robot should navigate to a point roughly 1.2 m short of that point, facing it — a genuinely useful, low-effort integration check that requires no other part of the pipeline to be running.

### 3.3 `bc_policy_node.py` (393 lines) — the learned policy

The counterpart node for both learned policies (Random Forest and MLP alike run through this exact same node — only the loaded `.joblib` file differs, selected via the `model_path` parameter). Structure: `BCPolicyNode.__init__`, `scan_callback`, `lidar_features` (computes `lidar_min_range`/`lidar_mean_range` from the live `LaserScan`), `robot_pose` (current pose from TF), `group_callback` (by far the largest method — assembles the full 7-feature vector from live sensor state, calls the loaded model's `.predict()`, converts the relative prediction to a map-frame goal, and applies `approach_guard` if enabled), `send_goal`, `goal_response_callback`, `goal_result_callback`.

The module-level `FEATURE_ORDER` constant is declared explicitly and commented as non-negotiable: `["lidar_min_range", "lidar_mean_range", "linear_x_prev", "angular_z_prev", "num_people", "group_bearing_rad", "group_scale_norm"]`, in that exact order — a mismatch here "silently produces garbage predictions rather than an error," so the feature-assembly code is written out explicitly rather than built dynamically. Three module-level constants exist purely to reconstruct one of those seven features live: `IMAGE_WIDTH = 640.0` (matching the training-time pixel normalisation), `TYPICAL_PERSON_WIDTH_M = 0.5` (an assumed adult shoulder width), and `ASSUMED_FOCAL_PX = 525.0` (a nominal RGB focal length) — together these let the node reconstruct an equivalent of `group_scale_norm` (originally a pixel-based apparent-size proxy for distance, since the training data had no depth) from the simulator's *true* metric distance to the group, which is exactly the train/deploy domain-shift limitation disclosed in Methodology Section 3.9.

The default model path is hard-coded to `approach_pose_random_forest_tuned.joblib`, and the docstring is candid about exactly why, quoting the actual offline numbers (0.365 m / 25.8° vs the untuned RF's 0.401 m / 29.3° and both MLP variants) and stating plainly that "the rule-based baseline still wins on position... and NO policy met the proposal's <20° orientation threshold" — the node's own comments do not oversell the model it loads.

### 3.4 `mission_node.py` (446 lines) — the scripted patrol tour

Runs the fixed five-waypoint patrol and arbitrates control with whichever policy node is active. Functions: `__init__`, `now_s`, `on_people`, `on_group`, `on_approach_start` / `on_approach_done` (the `/approach/start` and `/approach/complete` handshake that fixed fault 5.7, the goal-preemption race between mission and policy), `already_visited`, `unvisited_sightings`, `tick` (the main state-machine step), `send_waypoint`, `robot_xy`, `cancel_current_goal`, `on_response`, `on_result`, `arrived`, `retry_or_skip`, `complete`, `cluster_sightings` (groups multiple sightings of what might be the same group into one, for reporting purposes).

### 3.5 `gt_localisation_node.py` (164 lines) — ground-truth localisation

The smallest of the core nodes but arguably the most consequential single fix in the whole project (Methodology Section 3.6.3/5.5). A module-level `yaw_of()` helper extracts yaw from a quaternion; `GroundTruthLocalisation.__init__`, `on_models` (subscribes to Gazebo's `/gazebo/model_states`), `on_odom`, and `publish_tf` — computing and broadcasting `T_map_odom = T_map_base · T_odom_base⁻¹` continuously at 30 Hz, replacing the earlier static-transform approach that was correct only at startup and diverged progressively afterward.

### 3.6 `explore_node.py` (233 lines) — free-roam patrol (superseded)

An earlier, simpler exploration behaviour — patrol the room generically until a person is seen — later superseded for the final experiments by `mission_node.py`'s fixed, repeatable waypoint route, but retained in the package and still wired into the launch file behind an `explore` flag (default `false`) as an option for when no scripted mission is wanted. Functions: `__init__`, `now_s`, `on_group`, `cancel_patrol`, `tick`, `reached_current`, `robot_xy`, `send_patrol_goal`, `on_goal_response`, `on_result`.

### 3.7 `metrics_recorder_node.py` (463 lines) — the evaluation engine

Implements every simulation metric described in Methodology Section 3.7.2. `MetricsRecorderNode.__init__`, `load_groundtruth` (reads the world's `.groundtruth.json`), `scan_callback` (includes the self-hit calibration logic from fault 5.11 — observing the stationary robot's own minimum lidar return during a grace period and using it to set a corrected collision floor), `centroid_callback`, `robot_xy_yaw`, `sample` (the 10 Hz trajectory-sampling tick), `compute_cut_through` (containing nested `segments_intersect` and `orient` helpers — a textbook line-segment-intersection test, used to detect the group cut-through metric), `task_success` (implementing the corrected, ground-truth-based scoring logic from fault 5.12), and `finish` (writes the final per-trial JSON, containing both the summary metrics and the complete raw trajectory — the design choice that makes offline re-scoring via `rescore_sim_results.py` possible at all, without which the corrections in faults 5.11 and 5.12 could never have been retroactively applied to already-recorded trials).

### 3.8 Launch configuration — `group_approach.launch.py`

The single launch file that assembles the whole live pipeline, and it is a genuinely substantial piece of configuration engineering in its own right — worth documenting as an implementation artefact, not just a thin wrapper. It declares roughly twenty `DeclareLaunchArgument` entries, each with an explanatory `description` string written for a future user (or marker) rather than left undocumented: `policy` (`rule` / `bc` / `mlp` / and, notably, the historical model-generation aliases `bc_v2`, `mlp_v2`, `gb_v2`, `bc_ft`, `mlp_ft`, `gb_ft` — all routed through the *same* `bc_policy_node`, only the `.joblib` differing, with an explicit comment warning that passing an unrecognised policy name fails silently: the node simply never starts and the robot patrols with no approach policy at all), `metrics`, `groundtruth`, `model_path`, `approach_guard` (default `true` — the disclosed hybrid-intervention flag from Methodology Section 3.9, settable to `false` specifically so the *unmodified* model can also be evaluated if wanted), `output_dir`, `detector`, `oneshot`, `retrigger_period_s`, `edge_margin_px`, `dwell_time_s` (30 s default, with an explicit comment that it **must** stay below `max_approach_time` or the mission will cancel an approach mid-dwell), `max_approach_time` (60 s), `approach_budget_s` (300 s total per trial — note this is the launch file's own default, distinct from the 120 s figure quoted in `PROJECT_RECORD_POST_REPORT1.md` for the actual final experimental runs; the launch default is a generous ceiling and the specific experiments constrained it further via an explicit override), `group_distance_m` (1.5 m), `min_group_size` (2, with a comment explaining that a value of 1 would treat a lone person as a valid approach target and is not what the final experiments used), `mission` (true/false — whether to run the scripted patrol at all), `obstacle_wait` (15 s), `explore` (false by default — the scripted mission supersedes free-roam patrol for reported experiments), `idle_timeout`, `confidence` (0.45), and `standoff_distance` (1.2 m).

Two implementation details recorded directly in code comments are worth keeping, since they are exactly the kind of ROS 2 packaging gotcha that costs real debugging time if rediscovered: launch files must be installed explicitly in `setup.py`'s `data_files` or `ros2 launch` cannot find them at all (a very common and non-obvious omission); and every numeric `DeclareLaunchArgument` value is a *string* by construction, so every place a node expects an `int`/`float`/`bool` parameter, the launch file must wrap it in `ParameterValue(..., value_type=...)` explicitly, or ROS 2 rejects the type mismatch at node startup.

## 4. The `tiago_head_control` package (90 lines)

A small, earlier utility package, and — notably — the **only package in the repository with an actual test scaffold** (`test/test_copyright.py`, `test/test_flake8.py`, `test/test_pep257.py`, all standard `ament_*` lint tests rather than functional tests of the node's own behaviour). ## 7. The `scripts/` directory — the full offline and orchestration toolkit

Fifty-one Python scripts and roughly a dozen shell scripts, organised below by what stage of the project they actually serve rather than alphabetically, since the alphabetical listing (already given in full, with line counts, at the very top of this document's gathering notes) obscures how the pieces fit together.

### 7.1 Offline dataset extraction (turning raw session recordings into tabular data)

- `extract_training_table.py` (653 lines) — the largest single extraction script; reads one session's ROS1 bag files via `rosbags`, merges pose/LiDAR/detection topics on a common timestamp index via `pandas.merge_asof`, and writes the per-session training table.
- `extract_person_detections.py` (193 lines) — runs YOLOv8n on sampled frames (~1/second, using real frame timestamps from each session's frame manifest, not a naive fixed-interval sample) for the 22 sessions with no facial-landmark ground truth, writing `detected_people.csv` in the same schema as the facial-landmark summary so `extract_training_table.py` can treat it as a drop-in substitute.
- `inspect_dataset_session.py` (635 lines) — a diagnostic/exploratory tool that summarises one session folder's full contents; large because it handles many different file types and produces a detailed structured report per session.
- `split_dataset.py` (90 lines) — the session-level 70/15/15 train/validation/test split with the fixed seed (42) described in Methodology Section 3.1.
- `check_dataset_readiness.py` (201 lines) — scans every extracted `training_table.csv`, reporting row counts, session duration, and per-column completeness, run as a gate before training anything.
- `build_master_session_summary.py` (240 lines) — aggregates every session's individual `session_summary.json` into one master CSV/JSON table.

### 7.2 Early exploratory Behavioural Cloning (superseded, kept for the historical record)

- `train_baseline_model.py` (151 lines) — the project's very first BC attempt, predicting `cmd_vel` directly from robot-only features; its own docstring records, deliberately preserved, the lesson that absolute (x, y, yaw) as a feature actively hurt performance because it doesn't generalise across sessions recorded in different rooms — this single finding is the direct ancestor of the relative-pose design used everywhere in the final approach-pose model.
- `train_social_baseline_model.py` (172 lines) — the direct follow-up, adding human-position features (from facial landmarks or detected people) to test whether social awareness actually helped; kept as evidence the comparison was made rather than assumed.

### 7.3 The final approach-pose Behavioural Cloning pipeline

- `build_approach_pose_dataset.py` (232 lines) — the v1 label-construction script described in full in Methodology Section 3.4 (462 events, 70,555 rows).
- `train_approach_pose_model.py` (120 lines) — trains the Random Forest approach-pose model on the relative (Δx, Δy, Δyaw) target.

## 8. Testing and validation approach — stated honestly

There is no dedicated unit-test suite for `tiago_group_approach`'s own node logic, despite `pytest` being declared as a test extra in its `setup.py`. This is a genuine limitation, and it is compensated for in practice by four things rather than left as an unaddressed gap: (1) `tiago_head_control` does carry a real `ament_*` lint test scaffold (copyright, flake8, pep257), demonstrating the pattern was known and used where it was set up; (2) the offline ML pipeline is validated against real, held-out ground truth at every stage that matters — detector recall against face annotations, O-space estimation against 30 hand-labelled frames, model accuracy against fully held-out test sessions — which is a stronger check on *correctness* than a unit test would typically provide, even though it is not the same kind of test; (3) the diagnostic shell scripts (`check_sim_setup.sh`, `preflight_check.sh`) function as de facto integration tests, each checking one specific link in the live pipeline in a fixed, repeatable order; and (4) a genuine top-level test file, `tests/test_periodic_perception.py`, exists specifically to test the periodic-detection mode described in Section 3.1 above — the one piece of live-node logic that did receive a dedicated automated test, likely because its timing-sensitive threaded behaviour was judged too easy to silently break otherwise.
